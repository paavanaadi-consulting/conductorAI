Next.js Frontend
ui/frontend/src/
UI Layer

Purpose

The user-facing web application. Provides a graphical interface for business/technical analysts to create projects, upload YAML specifications, select which agents to run, monitor workflow progress in real-time, and review AI-generated pull requests.

Key Responsibilities

  • Render project creation form with YAML drag-and-drop upload, template selection, and component checkboxes
  • Detect if a GitHub repository already has an existing project and switch to update mode
  • Display real-time workflow progress via WebSocket connection (phase indicator, task counts, status badges)
  • Browse GitHub repos and pull requests, trigger AI-powered code reviews
  • Present review scores (complexity 1-10, quality 1-10), findings, and recommendations

Interactions

Calls →
All REST API calls via fetch() to localhost:8000/api/*. React Query (TanStack) manages caching, loading, and error states.
WebSocket (/api/ws)
Subscribes →
Opens WebSocket to /api/ws/workflow/{id} for real-time progress updates during workflow execution. Custom useWorkflow hook.

FastAPI Backend
ui/api/main.py
UI Layer

Purpose

The REST API server that bridges the web frontend to the ConductorAI core engine. Manages project persistence in SQLite, handles file uploads, serves YAML templates, and orchestrates the connection to GitHub via the GitHub App integration.

Key Responsibilities

  • Initialize ConductorAI engine on startup (lifespan context manager), register all 8 agents
  • Expose 6 router groups: projects, workflows, templates, github, upload, websocket
  • Persist project metadata, workflow runs, and PR reviews in async SQLite (aiosqlite)
  • Launch long-running workflows as background asyncio.create_task() to avoid blocking HTTP responses
  • CORS configured to allow Next.js frontend on port 3000

ConductorAI (Facade)
src/conductor/facade.py
Facade Layer

Purpose

The single entry point for the entire ConductorAI system. Implements the Facade pattern — hides all internal complexity (orchestration, agents, messaging, state) behind a clean, unified API. Manages the full lifecycle: initialization, agent registration, workflow execution, artifact management, and graceful shutdown.

Key Responsibilities

  • Initialize all subsystems in correct order: infrastructure → message bus → state manager → coordinator → workflow engine
  • Provide register_agent() / unregister_agent() for adding agents to the coordinator
  • Expose run_workflow(definition) as the primary execution method
  • Expose dispatch_task(task) for single-task execution
  • Expose generate_pipeline_yaml() for YAML generation
  • Manage artifact storage and context assembly
  • Support async with ConductorAI() as conductor: context manager pattern

Interactions

WorkflowEngine
Owns →
Creates WorkflowEngine in initialize(). Delegates run_workflow() calls to it.
AgentCoordinator
Owns →
Creates coordinator, routes register_agent() and dispatch_task() through it.
MessageBus
Owns →
Creates InMemoryMessageBus and passes to coordinator. Exposed as property.
StateManager
Owns →
Creates InMemoryStateManager for state persistence. Shared with coordinator and workflow engine.
ArtifactStore
Owns →
Creates InMemoryArtifactStore for saving agent work products.
ConductorService
← Wrapped by
The UI layer's ConductorService holds a reference to this facade instance.

WorkflowEngine
src/conductor/orchestration/workflow_engine.py
Orchestration Layer

Purpose

The phase orchestrator that executes multi-phase workflows. Takes a WorkflowDefinition and runs it through ordered phases: DEVELOPMENT → DEVOPS → MONITORING. Manages phase gates, sequential task execution within each phase, and the feedback loop mechanism when the MonitorAgent detects issues.

Key Responsibilities

  • Create WorkflowState and track lifecycle (PENDING → IN_PROGRESS → COMPLETED/FAILED)
  • Filter tasks by phase using PHASE_AGENT_TYPES mapping
  • Execute each phase's tasks sequentially via the AgentCoordinator
  • Check phase gates via PolicyEngine before advancing to the next phase
  • Handle feedback loops: when MonitorAgent reports has_issues: true, re-trigger DEVELOPMENT phase (up to max_feedback_loops = 3 times)
  • Save WorkflowState to StateManager after each task completion

Interactions

AgentCoordinator
Calls →
Calls coordinator.dispatch_task(task) for each task. The coordinator finds the right agent and executes the task.
StateManager
Reads/Writes →
Saves WorkflowState after each task result. Allows recovery and progress tracking.
PolicyEngine
Checks →
Calls policy_engine.check() at phase boundaries (phase gate pattern).
ArtifactStore
Writes →
Saves context artifacts from agent outputs (code, configs, reviews).
ConductorAI Facade
← Called by
Facade delegates run_workflow() here.

AgentCoordinator
src/conductor/orchestration/agent_coordinator.py
Orchestration Layer

Purpose

The central nerve center for agent lifecycle management and task dispatch. Maintains the registry of all agents, finds available (IDLE) agents by type, applies policy checks, dispatches tasks to the right agent, and syncs state after execution.

Key Responsibilities

  • Maintain agent registry (_agents dict: agent_id → BaseAgent)
  • Register agents: validate uniqueness, call agent.start(), sync state
  • Dispatch tasks: find IDLE agent of required type → policy check → agent.execute_task() → save result
  • Raise AgentError if no available agent or policy violation

Interactions

Manages →
Calls agent.start(), agent.execute_task(), agent.stop(). Tracks agent status.
StateManager
Writes →
After every dispatch: save_agent_state() + save_task_result().
PolicyEngine
Checks →
Before dispatch: checks max concurrent tasks, agent availability policies.
MessageBus
Publishes →
Broadcasts status updates when agents change state.

PolicyEngine
src/conductor/orchestration/policy_engine.py
Orchestration Layer

Purpose

Rule evaluation and enforcement layer (Strategy pattern). Contains a chain of pluggable Policy objects. Supports soft checks (return bool) and hard enforcement (raise on violation). Used for task dispatch validation and phase gate decisions.

Key Responsibilities

  • MaxConcurrentTasksPolicy — limit simultaneous running agents
  • TaskTimeoutPolicy — validate timeout values are within bounds (1-3600s)
  • PhaseGatePolicy — control phase transitions based on success rate thresholds
  • AgentAvailabilityPolicy — ensure target agent type exists and is available

Interactions

AgentCoordinator
← Called by
Coordinator calls check() before dispatching tasks to verify policies pass.
WorkflowEngine
← Called by
Engine calls check() at phase boundaries (phase gate) to decide if workflow can advance.

LLM Provider System
src/conductor/integrations/llm/
LLM Provider Layer

Purpose

Abstract interface for LLM API calls (Strategy pattern). All agents use the same BaseLLMProvider interface, making it trivial to swap between OpenAI, Anthropic, or Mock providers via configuration. The factory function create_llm_provider(config) creates the right implementation based on the provider setting.

Key Responsibilities

  • BaseLLMProvider (abstract) — defines generate(prompt) and generate_with_system(system, user)
  • OpenAIProvider — wraps OpenAI's Python SDK for GPT-4, GPT-4o, GPT-3.5-turbo
  • AnthropicProvider — wraps Anthropic's SDK for Claude 3 Opus, Sonnet, Haiku
  • MockLLMProvider — returns pre-defined responses for testing (no API calls)
  • create_llm_provider(config) — factory function that instantiates the right provider

Interactions

All 8 Agents
← Used by
Every agent calls self._llm_provider.generate_with_system() in its _execute() method.
ConductorService
← Created by
Service calls create_llm_provider(config) during initialization and passes it to each agent constructor.
OpenAI / Anthropic APIs
Calls →
Makes HTTP requests to external LLM APIs (or returns mock data in test mode).
